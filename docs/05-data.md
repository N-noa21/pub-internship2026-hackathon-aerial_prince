# 05. 商品データと検索

> 一覧に戻る: [README.md](README.md) ／ 前: [04-ending.md](04-ending.md) ／ 次: [06-snowflake.md](06-snowflake.md)

献上品に**実在する商品**を出せるかどうかが、このゲームのコンテンツ品質を決める。

## 方針（決定）

**楽天市場 商品検索 API で事前にカタログを作り、実行時はそのカタログから検索してエージェントに判定させる。**

<https://webservice.rakuten.co.jp/documentation/ichiba-item-search>

- 日本語・実在・画像付きの商品が手に入る
- **実行時に楽天 API を叩くことはしない。** 2026 年 2 月の仕様変更で送信元 IP / Referer の検査が厳格になり、
  **Snowflake から実行時に呼ぶのは現実的でない**（[tech/05-rakuten-api.md](tech/05-rakuten-api.md#結論-リアルタイムに叩かず事前バッチで取り込む)）
- 代わりに、**IP を登録できる開発者のマシンから事前バッチで取得**し、Snowflake のテーブルと内部ステージに焼き込む
- 結果として**実行時の外部通信がゼロ**になる。レギュレーション上の懸念も、デモ中の外部依存も消える

### この方針の帰結

| 論点 | どうなるか |
| --- | --- |
| 品揃え | 無限ではなく**カタログの範囲内**。だからこそ収集キーワードの設計が重要になる |
| 検索 | 自前のテーブルを引く。規模次第で**ベクトル検索 / Cortex Search が必要になりうる**（下記） |
| 画像 | 取り込み時にダウンロードして内部ステージへ。実行時に外部ドメインを踏まない |
| レイテンシ | 楽天 API の往復が消えるぶん速い |

### ベクトル検索は要るのか

**カタログの規模が決まってから判断する。** 実行時に楽天へ投げる案なら不要だったが、
自前カタログを引く方式になったので、**規模によっては必要**になる。

| カタログ規模 | 方式 |
| --- | --- |
| 〜数百件 | 全件を LLM に渡して選ばせる。検索基盤が要らない |
| 数千件 | キーワード・カテゴリで粗く絞る → LLM に渡す。**まずここを狙う** |
| 数万件〜 | ベクトル検索 or Cortex Search |

- `VECTOR_COSINE_SIMILARITY` <https://docs.snowflake.com/en/sql-reference/functions/vector_cosine_similarity>
- Cortex Search（ベクトル＋キーワードのハイブリッド。埋め込み管理が不要）
  <https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-search/cortex-search-overview>

ただし**「意味が近い商品」を引いても面白くない**という原則は変わらない。
「城が欲しい」に意味的に一番近いのは不動産であって、LEGO の城ではない。**素直な類似検索は正解を返してしまう。**
面白さは検索エンジンではなく、**検索語をどうズラすか**と**候補からどれを選ぶか**が作る。だから下の 2 段構えは維持する。

## 処理フロー

```
わがまま「でっかい城が欲しいのじゃ」
   ↓
[1] LLM が家臣 5 人分の「ズラした検索語」を作る
      商人   → "城 おもちゃ 大型"
      貴族   → "城 レゴ"
      騎士   → "姫路城 パズル"
      農民   → "ビニール温室 家庭用"
      宰相   → "城 見学 ツアー"（5 人目はまとも枠）
   ↓
[2] カタログ（item_catalog）を 5 本の語で引く
   ↓
[3] 返ってきた商品リストを LLM に渡し、家臣ごとに 1 件ずつ選ばせる
      ＋ その家臣の口調で口上を書かせる（構造化出力でまとめて取得）
   ↓
[4] 献上品カードとして表示
```

- **[1] のプロンプトが面白さの全て。** [ズラし方の型](02-mechanics.md#ズラし方の型プロンプト設計の中心)をそのまま指示に入れる。
- **属性ごとに検索語を変える**と多様性が出る。属性の語（「業務用」「高級」「食品」など）をクエリに足すのが手軽。
- 引けなかった語には**フォールバック**を用意する（カテゴリだけで引く／鉄板の献上品を返す）。カタログ方式では必ず起きる。
- [3] は「選ぶ＋口上を書く」を 1 回の構造化出力にまとめると、レイテンシが読める。

## 楽天 API の実務メモ

取得は**事前バッチ**で行う。手順・エンドポイント・登録の注意は [tech/05-rakuten-api.md](tech/05-rakuten-api.md) にまとめた。要点だけ：

| 項目 | 内容 |
| --- | --- |
| エンドポイント | **`openapi.rakuten.co.jp`**。旧 `app.rakuten.co.jp/services/api/` は 2026-05-14 に停止済み |
| 認証 | `applicationId` ＋ `accessKey`。**アプリ種別は「バックエンドサービス」**で登録し、実行元 IP を登録する |
| **送信元制限** | **Web アプリ登録＝Referer 検査（localhost 不可）／バックエンド登録＝固定 IP 検査。** これが実行時呼び出しを諦めた理由 |
| 画像 | **64px / 128px の正方形サムネイル**。ゲーム画面には小さい可能性がある。取り込み時に保存する |
| 保存の可否 | **商品情報・画像を保存して再利用してよいか、規約で必ず確認する**（カタログ方式の前提） |
| フィルタ | 成人向け・危険物・極端な価格帯は**取り込み時に落とす**。展示事故を防ぐ |

## リスクとフォールバック

**外部通信が使えるかどうかが前提条件になる。** ここが崩れると方針ごと変わるので、最初に確認する。

| リスク | 対策 |
| --- | --- |
| 実行時の外部通信 | **そもそも使わない設計にした**ので、レギュレーション上の懸念は商品データに関しては消える |
| カタログに無いわがままが来る | **これが一番起きる。** カテゴリだけで引くフォールバックと、鉄板の献上品を仕込んでおく |
| 面白い商品が引けないわがままがある | よくあるお題については、**手で選んだ鉄板の献上品**を仕込んでおく（お題ガチャと組み合わせると効く） |
| 画像が小さい・取れない | カード側のレイアウトを小さい画像前提で組んでおく。拡大は取れたらボーナス |

- 画像生成（王子アバター）を使う場合は、そちらだけ外部通信が必要になる（[06-snowflake.md](06-snowflake.md#画像生成王子アバター)）。

## 他の候補（比較）

| 候補 | 良い点 | 懸念 |
| --- | --- | --- |
| **楽天市場 商品検索 API → 事前カタログ**（採用） | 日本語・実在・画像あり。実行時の外部通信ゼロ | 品揃えがカタログの範囲に限られる。収集の手間。画像が小さい |
| Yahoo!ショッピング Web API <https://developer.yahoo.co.jp/webapi/shopping/> | 楽天が使えない場合の代替 | 同様の送信元制限があるか要確認。画像の扱いも要確認 |
| 自前キュレーションカタログ | ネタの質を保証できる。外部依存ゼロ | 収集コスト。品揃えが尽きるとリプレイ性が落ちる |
| Snowflake Marketplace のデータセット | Snowflake 内で完結 | 日本語商品データがあるか要調査。粒度も不明 |
| 公開データセット（Amazon Reviews / ABO 等） | 無料・大量・画像あり | ほぼ英語。ライセンス確認が必要 |
| LLM に商品名を生成させる | 実装が最速 | ハルシネーション。「実在する商品」の面白さが死ぬ |

### エージェント向けコマース API / MCP

「エージェントが商品を検索して買う」ための標準も出てきているが、**今回は楽天 API で足りる**ので採用しない。
将来の差し替え先として記録だけ残す。

- **ACP（Agentic Commerce Protocol）** — OpenAI と Stripe が策定
  <https://github.com/agentic-commerce-protocol/agentic-commerce-protocol>
  - 2026-04-17 のリリースで cart / feed / orders / 認証 と MCP 互換が入った
    （出典は二次情報: <https://agenticplug.ai/current-state-of-agentic-commerce>）
- **UCP（Universal Commerce Protocol）** — Google 陣営が 2026 年 1 月に発表
  （出典は二次情報: <https://opascope.com/insights/ai-shopping-assistant-guide-2026-agentic-commerce-protocols/>）

これらは主に**「加盟店がフィードを提供し、エージェントが決済まで行う」ための仕組み**であり、
誰でも叩ける横断的な商品検索 API ではない。今回必要なのは**検索と画像だけ**なので、オーバースペックになる。

## その他の検討ポイント

- LLM の役割は「商品をゼロから考える」ではなく「**検索結果から選んで、家臣のキャラで口上を述べる**」。ここは崩さない。
- 家臣は 5 人固定なので、**1 回のわがままに対して毛色の違う 5 件**を揃える必要がある。属性ごとの検索語で差をつける。
- **主催側から提供されるデータセットがあるか**を確認する。あればそちらを優先する可能性がある。
