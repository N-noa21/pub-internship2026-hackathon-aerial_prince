# 03. 演出・UI

> 一覧に戻る: [README.md](README.md) ／ 前: [02-mechanics.md](02-mechanics.md) ／ 次: [04-ending.md](04-ending.md)

## 舞台

- 舞台は**謁見の場**。王子は玉座に座り、正面に家臣 5 人の列。
- 家臣は毎回同じ顔ぶれなので、立ち絵・口癖・登場音に投資する価値がある（[02-mechanics.md](02-mechanics.md#家臣5-人固定)）。
- LLM の生成待ちは「家臣が集まっております…」の演出で隠す。

## タイトル画面

- 中央に大きくロゴ **「下民ショッピング」**、その下に **START ボタン**ひとつ。それだけ。
- 玉座の間を背景に、金の縁取りと垂れ幕でロイヤルに。ロゴは重めのセリフ体で格式を出す。
- ルール説明は**一行だけ**添える（例: 「わがままを申せ。気に入らぬ者は斬るがよい」）。
  展示では読まれないので、遊べばわかる形にしておく。
- START を押したら、そのままわがまま入力へ。**画面遷移は最小限**にする。

## UI デザインの方向性

**ロイヤル感 × シンプル。** 王宮・玉座の間の空気を出しつつ、画面そのものは徹底的に単純にする。
装飾を足すのではなく、**シンプルな骨格に、ロイヤルな要素を数点だけ効かせる**。

### なぜシンプルにするか

- 展示で初見の人が**説明なしで 2 分で遊べる**必要がある
- 主役は献上品と打ち首の演出。UI が主張すると、その 2 つが埋もれる
- 装飾が少ないほど、AI に生成させるアニメーションと馴染ませやすい

### 具体的な方向

| 要素 | 方針 |
| --- | --- |
| 配色 | **3 色に絞る。** 緋色（玉座の赤）＋ゴールドのアクセント＋生成り（羊皮紙）。背景は暗めの赤／紺で沈める |
| 装飾 | **枠と背景にだけ閉じ込める。** 金の縁取り、垂れ幕、紋章。情報を載せる面は無地にして可読性を守る |
| タイポ | 見出しはセリフ体で格式を出し、本文はゴシックで可読性優先。和風（毛筆・明朝）に寄せるか洋風（王宮）に寄せるかは要決定 |
| 画面構成 | **1 画面 1 アクション。** 中央に献上品カード 1 枚、下に「採用」「打ち首」の 2 ボタンだけ |
| 列の表現 | 残り何人かは画面端に小さく 5 個のインジケータで示す。列そのものを常時描画して情報を増やさない |
| ボタン | 「打ち首」は緋色＋金縁で一番目立たせる。**押すこと自体が気持ちいい**サイズと反応にする |
| 羊皮紙 | 献上品カードと診断レポートは羊皮紙の質感で統一すると、それだけで世界観が出る |

### 実装メモ

- Streamlit の既定の見た目は**そのままだと王宮に見えない**。テーマ設定＋カスタム CSS で潰す作業を工数に見込む。
- **Web フォントを外部ドメイン（Google Fonts 等）から読めるかは要検証。**
  Streamlit in Snowflake は CSP により外部ドメインからのスクリプト読み込みを禁じている
  （<https://docs.snowflake.com/en/developer-guide/streamlit/limitations>）。フォントも弾かれる場合は**同梱**するか、
  システムフォント（游明朝・ヒラギノ明朝など）で組む。
- 凝った見た目が必要な画面（謁見・打ち首・エンディング）は、Streamlit のウィジェットで組むより
  **`st.components.v1.html` に HTML/CSS ごと流し込むほうが早くて綺麗**になる可能性が高い。

## 王子アバター（カメラ機能）

- カメラのある端末では**自分の写真を撮影 → 王子風に変換**して主人公にする。
  - 王子の衣装を着せる／横に白馬を置く／自分の写真が喋っているように見せる
  - カメラが無い端末は既定アバターにフォールバック
- 撮影 UI は Streamlit の `st.camera_input` で実現できる。**Streamlit in Snowflake でも GA**（2025-03-24 の Streamlit in Snowflake リリースノートで一般提供化）。
  - サポート状況・制限の一次情報: <https://docs.snowflake.com/en/developer-guide/streamlit/limitations>
- 王子風への**画像変換**の実現手段は [06-snowflake.md](06-snowflake.md#生成-ai-の置き場所) を参照（Snowflake 内に画像生成モデルが見当たらないため、ここが最大の技術リスク）。
- このアバターは**エンディングでも使い回す**（[04-ending.md](04-ending.md#カメラ写真の再利用)）。

## 打ち首アニメーション

**ここが弱いとゲームが成立しない。** 最も時間をかける部分。

- 直接的・残虐な表現は避け、**理不尽だがコミカルな退場**にする。
- **1 種類では足りない。** 1 プレイで最大 5 回、2 周目もあることを考えると、複数用意して出し分ける。
- ただし**自分たちで手描きのアニメーションを作る体力はない**。まず下の 4 案を作り込み、
  足りなければ **AI に増やしてもらう**（下記「量産の仕組み」）。

### 退場アニメーション案

| # | 演出 | 動き | 台詞（例） |
| --- | --- | --- | --- |
| 1 | 落とし穴 | 足元の床が開き、真下に落ちて消える | 「ぬわーっ」 |
| 2 | 衛兵に連行 | 両脇を抱えられ、じたばたしながら横に引きずられる | 「お待ちを！お待ちをー！」 |
| 3 | 大砲で発射 | 斜め上に打ち上がり、キラッと星になって消える | 「とんでもございませーん」 |
| 4 | 却下スタンプ | 巨大なハンコが降ってきて「却下」、ぺしゃんこになる | （無言） |

### 出し分け

ランダムだけにすると意味が薄い。次の 3 つで選ぶと「効いてる」感じが出る。

| 選ぶ基準 | 例 |
| --- | --- |
| 判決理由（[02-mechanics.md](02-mechanics.md#判決理由任意入力)） | 「無礼者」→ 大砲、「安っぽい」→ 却下スタンプ、「趣味ではない」→ 落とし穴 |
| 家臣の属性 | 農民 → 落とし穴、貴族 → 却下スタンプ、宰相 → 大砲（正論を吹き飛ばす） |
| 連続打ち首数 | 斬るほど派手になる（落とし穴 → 連行 → スタンプ → 大砲）。**5 人目は一番派手なものを固定で出す** |

- 同じプレイ中に**同じ演出を 2 回出さない**だけでも、体感の豊かさが変わる。
- 演出が増やせたら、この出し分け表に足していく。

## アニメーション量産の仕組み（AI に作らせる）

手で何種類も作るのは重い。**AI に作らせる前提で、最初に「型」を決める。**
型さえ固まれば、演出の追加はハッカソン期間中いつでもできるようになる。

> **実装仕様は [tech/04-animation-spec.md](tech/04-animation-spec.md) にまとめた。** そのまま AI への指示文として使える。

### 方針: 実行時ではなく「開発時」に生成する

- **開発時**に AI エージェント（Cortex Code / Claude Code など）にまとめて書かせ、**実行時は選んで再生するだけ**にする。
  - 実行時に生成しないので**動作が安定し、待ち時間ゼロ**
  - 出来の悪いものは**人間が捨てられる**（品質のコントロールが効く）
  - 生成コストがプレイ回数に比例しない
- 実行時生成（毎回違う打ち首が出る）はネタとして強いが、崩れ・失敗・待ち時間のリスクがある。
  やるなら**開発時に作ったストックをフォールバック**として必ず持つ。

### 型（AI に渡すコントラクト）

**1 演出 = 1 ファイル**。全ファイルが同じ前提・同じ DOM に対して書かれるようにする。これが量産の肝。

```
animations/
  01-fall.css        ← 落とし穴
  02-drag.css        ← 衛兵に連行
  03-cannon.css      ← 大砲
  ...
```

- **DOM は固定**。演出側は「決められた要素にアニメーションを当てる」だけにする。

```html
<div class="stage">           <!-- 謁見の間（背景） -->
  <div class="victim">        <!-- 退場する家臣＋献上品のまとまり -->
    <img class="retainer">    <!-- 家臣 -->
    <img class="item">        <!-- 献上品 -->
  </div>
  <div class="fx"></div>      <!-- 演出用の自由レイヤー（穴・ハンコ・花火など） -->
</div>
```

- 各ファイルが守るルール（**そのまま AI への指示文にする**）:
  1. 対象は `.victim` と `.fx` のみ。`.stage` の背景は変更しない
  2. **CSS のみ**で完結させる。JS を使わない
  3. **外部リソースを読み込まない**（CSP で弾かれる。[実装上の制約](#実装上の制約streamlit-in-snowflake)）。絵文字と CSS 図形で作る
  4. `@keyframes` 名とクラス名に**ファイル固有の接頭辞**を付ける（衝突防止。例 `a03-`）
  5. 再生時間は **1.2 秒以内**。終了時に `.victim` が完全に不可視になっている
  6. 発火は `.stage[data-anim="03-cannon"]` セレクタ配下でのみ有効にする
  7. `prefers-reduced-motion` に配慮した控えめ版も併記する

### 生成 → 採否のフロー

1. 上のコントラクトと[演出案の表](#退場アニメーション案)を AI に渡し、**まず 4 案を書かせる**（余裕があれば追加案も）
2. **プレビューギャラリー**（全演出を並べてボタンひとつで再生できるだけの HTML）で一覧確認する
   - これを最初に作っておくと、量産と選別が一気に楽になる。**優先度が高い**
3. 見て面白かったものだけ採用、微妙なものは捨てるか、その場で AI に直させる
4. 採用したファイル名を、出し分けのルール（判決理由・属性・コンボ）に紐づける

### 実装上の制約（Streamlit in Snowflake）

出典: <https://docs.snowflake.com/en/developer-guide/streamlit/limitations>

- `st.components.v1.html`（iframe）は**ウェアハウスランタイム・コンテナランタイムの両方でサポート**。
  → **打ち首アニメーションは iframe に HTML/CSS を流し込むのが現実的。**
- **Custom Components v2 はコンテナランタイムでのみサポート**（ウェアハウスランタイムでは非対応）。
- **CSP により、外部ドメインからスクリプトを読み込めない。** ライブラリを使うなら**同梱**する。
  → 素の CSS アニメーションに寄せるほど安全で、**AI にも書かせやすい**（上の型がまさにその形）。
- ウェアハウスランタイムには表示データに 32MB のメッセージサイズ上限がある（コンテナランタイムは既定 200MB、設定変更可）。

## モバイル・音

- カメラを使うなら実質スマホ前提になるため、**縦画面での見え方**を最初に決める。
- 効果音・BGM を鳴らせるかは要検証（[07-open-questions.md](08-open-questions.md)）。打ち首は音があると一気に良くなる。
